# בונה האתרים: הלקוח מספר, האתר נבנה

מטרה: בעל עסק ממלא את הפרטים בשיחה עם צ׳אט, מקבל דמו של **האתר שלו**, מבקש תיקונים באותה שיחה, מאשר ומשלם, והאתר נבנה. כפיר מאשר לפני שהאתר עולה לאוויר.

**מצב: שלב 1 בנוי.** הדף לבעל העסק: `/build/`. הדף של כפיר: `/build/admin/`. ההפעלה בסוף המסמך ("להדליק את הבונה").

## ההחלטות

| נושא | ההחלטה |
| --- | --- |
| מי מאשר | הלקוח מאשר את הדמו, ואז כפיר מאשר לפני פרסום |
| מתי משלמים | אחרי שהלקוח אישר את הדמו, לפני הבנייה |
| תבנית ראשונה | אינסטלטור (מהדמו `demos/plumber/` ומהאתר `clients/sample-plumber/`) |

## המסלול

```
שיחה בצ׳אט ──► קובץ תוכן ──► דמו בקישור פרטי ──► תיקונים בצ׳אט ──► "מאשר"
                                                                     │
         אתר באוויר ◄── פרסום ◄── כפיר מאשר ◄── תשלום הקמה ◄─────────┘
```

1. **שיחה.** הצ׳אט שואל כמו בשיחת היכרות, שאלה אחת בכל פעם: שם העסק, אזור, שירותים, טווחי מחיר שמוכנים לפרסם, זמן חזרה שהעסק עומד בו, וואטסאפ, טלפון לשיחות. ואז: "תעלו 3–5 תמונות שלכם ושל העבודה".
2. **דמו.** תוך דקה: קישור לדמו בטלפון, עם התוכן והתמונות של העסק, מסומן "טיוטה".
3. **תיקונים.** "תוריד את הדוד", "תחליף את התמונה הראשונה", "הצבע כהה מדי". הצ׳אט מתקן, והדמו מתעדכן באותו קישור.
4. **אישור הלקוח.** כפתור "מאשר את האתר" בתוך הדמו. אחריו קישור לתשלום ההקמה (מלא או 3 תשלומים, לפי המחירון).
5. **אישור כפיר.** כפיר מקבל וואטסאפ: "אתר חדש מחכה לאישור", עם קישור לדמו. בלוח הניהול: "לפרסם" או "להחזיר ללקוח" עם הערה.
6. **פרסום.** התיקייה `clients/<slug>/` נכתבת לריפו, נוצרת שורה במערכת הלידים, וההעלאה האוטומטית מעלה את האתר.

מה נשאר ידני, כי אי אפשר אחרת:
- **וואטסאפ:** אימות המספר ב-Meta ואישור התבניות. בינתיים האתר עובד, והטופס פותח וואטסאפ.
- **דומיין:** קנייה על שם הלקוח.
- **Netlify:** פתיחת האתר בחשבון של הלקוח (חמש דקות). לחלופין מפרסמים בחשבון של כפיר ומעבירים אחר כך.

## איך זה בנוי

### תבנית = דמו + קובץ תוכן

בדמואים הטקסט כתוב בתוך ה-HTML. בתבנית, כל טקסט הוא שדה. כל תבנית היא קובץ אחד ב-`demos/netlify/lib/templates/`, עם:
- השדות: מה יש, מה חובה, אורך מקסימלי, ואיזה שדה הוא עובדה שרק הלקוח קובע (שנים בתחום, אחריות, מחירים).
- `render`: הדף, דף הפרטיות והצהרת הנגישות, מהשדות. שדה ריק בטיוטה מסומן במסגרת מקווקוות; באתר האמיתי הוא פשוט לא מופיע.

הצ׳אט ממלא שדות ולא כותב HTML, ולכן העיצוב לא נשבר. בונים את התבנית מ-`clients/sample-plumber/`, כי הוא כבר נקי מכל סימני דמו, עם דפי פרטיות ונגישות, וכבר מחובר למערכת הלידים.

### הצ׳אט

פונקציה ב-Netlify (`/api/builder/chat`), Claude דרך ה-SDK הרשמי. בכל תור Claude מחזיר JSON לפי סכמה קבועה (structured outputs): הודעה ללקוח, ועדכון לשדות. העדכון נבדק מול הסכמה של התבנית לפני שנשמר: אורך, טלפון ישראלי, מספרים. ערך שלא עבר לא נשמר, והלקוח רואה בסוף התשובה מה לא עודכן ולמה.

התבנית היא קובץ אחד, `demos/netlify/lib/templates/plumber.mjs`: השדות (`FIELDS`, `SERVICES`, `TOWNS`, `PHOTOS`) ופונקציית `render`. עובדות (שנים, אחריות, מחירים, זמן חזרה) רק מפי הלקוח. טקסט (כותרת, פסקת פתיחה) הצ׳אט מציע, ומראה ללקוח לפני שהוא נכנס.

היסטוריית השיחה נשמרת כטקסט בלבד ורק גדלה, והמצב הנוכחי של הטיוטה נכנס רק להודעה האחרונה. כך תחילת הבקשה קבועה ונשמרת במטמון של Claude. תור שנכשל לא נשמר, והלקוח שולח שוב.

כללים בהנחיות של הצ׳אט:
- רק עובדות שהלקוח אמר. שדה שאין עליו תשובה נשאר ריק, ולא ממציאים.
- העברית לפי כללי הבית: קצרה, ברבים, בלי הבטחות מוגזמות.
- הצ׳אט לא מבטיח לקוחות, לא מבטיח מקום בגוגל ולא קובע מחירים במקום הלקוח.

### הדמו

פונקציה מרכיבה את התבנית עם קובץ התוכן ומגישה אותה בכתובת `/draft/<id>?k=<key>`, עם `noindex`, בלי מטמון, ובלי להעביר את הקישור הלאה (`no-referrer`). כל ערך עובר escaping, ולכן שום טקסט של הלקוח או של הצ׳אט לא שובר את הדף. בדיקת האיכות (`qa-page`) ובדיקת העברית רצות על מה שהתבנית מייצרת בכל `check-all.sh`: אתר מלא, אתר עם המינימום, וטיוטה ריקה.

### תמונות

הדפדפן מקטין את התמונה (עד 1600 פיקסל) ומקודד אותה מחדש ל-WebP, או ל-JPEG באייפון. הקידוד מחדש מוחק גם את נתוני המיקום (EXIF). הפונקציה מקבלת רק JPEG או WebP עד 1MB ושומרת ב-Supabase Storage (דלי `builder`). ארבע מסגרות: תמונה של בעל העסק ושלוש עבודות. לפני ההעלאה הלקוח מסמן שהתמונות שלו ושמותר לפרסם אותן.

### טבלה חדשה: `ls_drafts`

| עמודה | מה |
| --- | --- |
| `id`, `edit_key` | הקישור הפרטי (רק hash של המפתח נשמר) |
| `template` | `plumber` |
| `content` | קובץ התוכן (jsonb) |
| `photos` | רשימת התמונות והחיתוכים |
| `status` | `draft` → `client_approved` → `paid` → `published`, או `returned` עם הערה |
| `messages` | השיחה, לצורך המשך (טקסט בלבד) |
| `owner_phone` | של בעל העסק, לחזרה אליו |
| `package`, `plan` | החבילה ואופן התשלום שהלקוח בחר באישור |
| `rev` | עולה בכל שמירה, כדי ששני חלונות לא ידרסו זה את זה |

הטבלה בקובץ `supabase/lead-system/0002_site_builder.sql`, באותו פרויקט של מערכת הלידים.

### תשלום וחשבונית

הלקוח משלם בדף תשלום של מערכת חשבוניות ישראלית שיש לה גם סליקה, והקבלה או החשבונית יוצאת לבד. המערכת שולחת לנו webhook כשהתשלום עבר, והטיוטה מסומנת `paid`.

| מערכת | מה יש | מה לבדוק לפני שבוחרים |
| --- | --- | --- |
| **Morning (חשבונית ירוקה)** | דף תשלום וסליקה, הפקת מסמך אוטומטית אחרי תשלום, API ו-webhook מסוג `payment/received` | ה-API, ה-webhooks והסליקה במסלול Best ומעלה. הרשאה חד-פעמית ברשות המסים להפקה אוטומטית |
| **SUMIT** | דפי תשלום וסליקה, חשבונית שנוצרת אוטומטית בכל תשלום (ברירת מחדל), API מפורט, מודול הוראות קבע | המחירון (המקורות סותרים לגבי המסלול החינמי ו-API) |
| iCount | API V3 להפקת מסמכים, דפי תשלום, מסוף ב-30 ₪ לחודש | |

ההמלצה: המערכת שכפיר כבר עובד איתה. אם עוד אין, SUMIT או Morning, כי בשתיהן התשלום והמסמך יוצאים ביחד, ויש webhook שמסמן את הטיוטה כ"שולם".

איך זה מתחבר:
1. הלקוח לוחץ "מאשר", ונוצר לו קישור תשלום, מלא או בשלושה תשלומים, עם מזהה הטיוטה.
2. אחרי התשלום מערכת החשבוניות מפיקה את המסמך ושולחת webhook ל-`/api/builder/paid`.
3. הפונקציה בודקת את הסוד (Secret) של ה-webhook, ומאמתת את התשלום מול ה-API של המערכת לפני שהיא מסמנת `paid`. לא סומכים על הודעה שלא אומתה.
4. כפיר מקבל התראה: "שולם, מחכה לאישור שלך".

התשלום החודשי (150 או 500 ₪) מוגדר כהוראת קבע במערכת החשבוניות, לא אצלנו. כשהוראת הקבע נעצרת, כפיר מסמן `active = false` במערכת הלידים. אוטומציה לזה נשארת לשלב 3.

**עוסק פטור** מוציא קבלה ולא חשבונית מס. מגדירים את סוג המסמך במערכת לפי סוג העוסק של כפיר.

### פרסום

כפיר לוחץ "לפרסם" ובוחר שם תיקייה, והפונקציה כותבת לריפו דרך ה-GitHub API, בקומיט אחד, את `clients/<slug>/`: שלושת הדפים, `_headers`, `CLIENT.md` בלי פרטים פרטיים, הסקריפטים (אותם קבצים כמו ב-`clients/sample-plumber/assets/`) והתמונות. היא לא דורסת תיקייה של אתר אחר. בחבילת נציג AI נוצרת גם שורה במערכת הלידים, וכפיר מקבל פעם אחת את קישור הפאנל לבעל העסק.

`netlify.json` לא נכתב: כפיר מוסיף אותו אחרי שהאתר ב-Netlify קיים. המשך התהליך כמו היום (`CLIENT_SITES.md`): אתר ב-Netlify, `netlify.json`, דומיין, ו-`allowed_origins` במערכת הלידים.

## להדליק את הבונה

1. **טבלה ודלי.** ב-Supabase של מערכת הלידים: SQL Editor, להדביק את `supabase/lead-system/0002_site_builder.sql`, Run.
2. **משתני סביבה ב-Netlify** (בנוסף למה שכבר יש למערכת הלידים):

   | משתנה | מה |
   | --- | --- |
   | `ANTHROPIC_API_KEY` | כבר קיים בשביל הצ׳אט של האתר |
   | `GITHUB_TOKEN` | GitHub > Settings > Developer settings > Fine-grained tokens. רק הריפו הזה, הרשאת Contents: Read and write. תוקף: שנה, ותזכורת לחדש |
   | `BUILDER_DAILY_MAX` | לא חובה. כמה טיוטות חדשות ביום, לכולם יחד (ברירת מחדל 40) |
   | `PAY_URL_AI`, `PAY_URL_AI_THREE`, `PAY_URL_PRESENCE` | לא חובה. דפי תשלום קבועים של מערכת החשבוניות. בלעדיהם הלקוח רואה "נשלח לכם קישור לתשלום בוואטסאפ" |
   | `BUILDER_AI_TIMEOUT_MS` | לא חובה. ברירת מחדל 25000. אם Netlify עוצר פונקציות אחרי 10 שניות, לשים 9000 כדי שהלקוח יקבל "נסו שוב" מסודר |

3. **התראה לכפיר.** כשלקוח מאשר, ההתראה יוצאת דרך מערכת הלידים, לעסק `kfir` (אפשר לשנות ב-`BUILDER_ALERT_CLIENT`). בלי וואטסאפ מחובר, הטיוטה עדיין מופיעה ב-`/build/admin/` תחת "לטיפול".
4. **בדיקה.** לפתוח `/build/`, לבנות אתר בדוי עד הסוף, לסמן "שולם" ב-`/build/admin/`, לפרסם לתיקייה `test-builder`, ולמחוק אותה מהריפו אחרי שבדקתם.

### מה כפיר עושה בכל אתר

| הלקוח | כפיר, ב-`/build/admin/` |
| --- | --- |
| אישר את הטיוטה | מקבל וואטסאפ. פותח "תצוגה" ובודק כל עובדה ותמונה. שולח קישור לתשלום אם אין `PAY_URL_*` |
| שילם | "התשלום התקבל". אם משהו לא בסדר: "להחזיר ללקוח" עם הערה, והלקוח רואה אותה מעל הצ׳אט |
| - | "לפרסם", שם תיקייה באנגלית. שומרים את קישור הפאנל ושולחים לבעל העסק בפרטי |
| - | ממשיכים לפי `CLIENT_SITES.md`: אתר ב-Netlify, `netlify.json`, דומיין, ומספר הוואטסאפ ב-Meta |

### בדיקות

`bash scripts/check-all.sh` מריץ גם את הבונה: `scripts/tests/site-builder.test.mjs` (כל ה-API מול Supabase, Storage, Claude, GitHub ו-WhatsApp מדומים), `scripts/tests/builder-page.test.mjs` (הדף בדפדפן, בטלפון ובמחשב, מההתחלה ועד האישור), ו-`qa-page` ובדיקת העברית על מה שהתבנית מייצרת.
